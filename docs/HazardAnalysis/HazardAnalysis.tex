\section{Introduction}\label{sec:intro}

This section introduces Verity, explains the engineering purpose of this Hazard Analysis (\HA{}), defines the safety terminology used throughout, and outlines the document structure.

\subsection{System Context}
Verity is a user-triggered Chromium browser extension and backend analysis pipeline developed by Team~23 in McMaster University's SFWRENG 4G06 Capstone course. It helps web readers, students, educators, and community moderators evaluate selected webpage text and static images for Artificial Intelligence (\AI{}) generation and manipulation signals, presenting source-tagged evidence, explicit limitations, and next verification steps.

Whereas physical control systems risk kinetic or thermal harm, Verity operates as socio-technical decision-support software that processes arbitrary, potentially sensitive web inputs. Consequently, Machine Learning (\ML{}) misclassifications, ungrounded explanations, race conditions, or data leaks inside Verity create non-physical \textbf{harm}: false academic or reputational accusations, financial deception, privacy breaches, and browser or service compromise.

\subsection{Purpose of This Document}
This document establishes Verity's safety controls by: (1)~bounding extension, service, external-provider, and offline harness components (\hyperref[comp:C1]{C1}--\hyperref[comp:C7]{C7}, Section~\ref{sec:boundaries}); (2)~making conservative assumptions explicit (\hyperref[assump:A1]{A1}--\hyperref[assump:A5]{A5}, Section~\ref{sec:assumptions}); (3)~tracing failures to harms and controls in \FMEA{} (\hyperref[haz:H1]{H1}--\hyperref[haz:H10]{H10}, Section~\ref{sec:fmea}); and (4)~synchronizing derived requirements (\hyperref[SR1]{SR1}--\hyperref[SR9]{SR9}, Section~\ref{sec:safety-reqs}) with the companion \SRS{} \cite{VeritySRS2026} and milestone plan (Section~\ref{sec:roadmap}).

\subsection{Safety Definitions}\label{subsec:hazard-def}
Adapted from Leveson \cite{Leveson2011} and IEC 60812 \cite{IEC60812}: a \textbf{hazard} is a software state or condition within Verity (\hyperref[comp:C1]{C1}--\hyperref[comp:C7]{C7}) that, with foreseeable triggers (hostile inputs, domain shift, timeouts, or automation bias), can cause harm; a \textbf{failure mode} is how a component deviates from design intent (e.g., mapping a timeout to ``low risk''); and \textbf{harm / loss} is real-world stakeholder damage (wrongful accusation, deception, confidentiality breach, or invalid engineering claims).

\subsection{Document Structure}
Section~\ref{sec:scope} categorizes losses and direct standards. Section~\ref{sec:boundaries} defines system boundaries (\hyperref[comp:C1]{C1}--\hyperref[comp:C7]{C7}); Section~\ref{sec:assumptions} records \hyperref[assump:A1]{A1}--\hyperref[assump:A5]{A5}. Section~\ref{sec:fmea} presents the \FMEA{} worksheet and open verification register. Section~\ref{sec:safety-reqs} states \hyperref[SR1]{SR1}--\hyperref[SR9]{SR9} and traceability. Section~\ref{sec:roadmap} schedules delivery, followed by references, GenAI disclosure (Section~\ref{sec:ha-genai}), and reflections (Section~\ref{sec:ha-reflection}).

\section{Scope, Stakeholder Losses, and Standards}\label{sec:scope}

This analysis covers both the live browser assessment path (\hyperref[comp:C1]{C1}--\hyperref[comp:C6]{C6}) and offline benchmark evaluation (\hyperref[comp:C7]{C7}). System failures can cause six categories of stakeholder harm:

\begin{enumerate}[leftmargin=*, noitemsep]
    \item \textbf{Reputational Accusation \& Cultural Fairness Harm (\hyperref[haz:H1]{H1}, \hyperref[haz:H5]{H5}):} Flagging authentic prose or photography as synthetic—especially with accusatory framing—can wrongly accuse innocent writers; detectors show elevated false-positive rates (\FPR{}) on non-native English (\ESL{}) prose \cite{Liang2023ESL}, and social platforms strip \EXIF{}/\CTwoPA{} camera tags.
    \item \textbf{Financial \& Civic Deception Harm (\hyperref[haz:H2]{H2}, \hyperref[haz:H6]{H6}):} Missed synthetic scams or silent timeouts rendered ``low risk'' mislead users on high-stakes listings or news.
    \item \textbf{Automation Bias \& Epistemic Harm (\hyperref[haz:H3]{H3}, \hyperref[haz:H5]{H5}, \hyperref[haz:H8]{H8}):} Uncalibrated percentages (``91\% fake''), injected citations, or stale async overwrites erode critical verification.
    \item \textbf{Privacy \& Confidentiality Loss (\hyperref[haz:H4]{H4}, \hyperref[haz:H9]{H9}):} Unscoped DOM scraping, unconsented external transfers, retained \PII{} payloads, or session leaks violate user privacy and \PIPEDA{}.
    \item \textbf{Client Security \& Availability Loss (\hyperref[haz:H7]{H7}):} Unsanitized web payloads enable \XSS{}, while decompression bombs or valid traffic bursts cause Denial of Service (\DoS{}).
    \item \textbf{Scientific Validity Loss (\hyperref[haz:H10]{H10}):} Split leakage, hidden abstentions, or non-reproducible benchmarks misguide model selection.
\end{enumerate}

\section{System Boundaries and Components}\label{sec:boundaries}

Figure~\ref{fig:hazard-boundary} defines Verity's software boundary, separating the seven internal components analyzed by FMEA (\hyperref[comp:C1]{C1}--\hyperref[comp:C7]{C7}) from external actors and infrastructure. Notice the operational trust boundary: \hyperref[comp:C1]{C1}--\hyperref[comp:C2]{C2} run inside the desktop Chromium extension; \hyperref[comp:C3]{C3}--\hyperref[comp:C6]{C6} run inside the \textbf{team-controlled analysis service} (either locally on the user's machine or on a Team~23-managed host reached over Transport Layer Security (\TLS{}) / \HTTPS{}); any \textbf{optional third-party analysis provider} sits \emph{outside} this boundary, remains disabled unless its retention terms match zero-persistence policy, and receives live content only after explicit per-request consent (\SRS{} \texttt{FR8}); and \hyperref[comp:C7]{C7} runs strictly offline on developer or CI machines with public datasets, never touching extension user traffic.

\subsection{Components Inside the System Boundary (\texttt{C1}--\texttt{C7})}
\begin{enumerate}[leftmargin=*]
    \item \phantomsection\label{comp:C1}\textbf{C1 --- Browser Extension Capture \& Permission Controller:} Desktop Chromium \MVThree{} content/background logic. Captures only explicit user selections via least-privilege active-tab access and previews modality bounds prior to submission (\texttt{FR1}, \hyperref[SR8]{SR8}; hazard \hyperref[haz:H4]{H4}).
    \item \phantomsection\label{comp:C2}\textbf{C2 --- Result Display \& Uncertainty \UI{}:} Isolated extension result card rendering the five request states, source-tagged evidence items, false-positive warning, uncertainty limitations, and next verification steps (\texttt{FR3}--\texttt{FR7}, \hyperref[SR1]{SR1}--\hyperref[SR5]{SR5}; hazards \hyperref[haz:H1]{H1}, \hyperref[haz:H2]{H2}, \hyperref[haz:H5]{H5}, \hyperref[haz:H8]{H8}).
    \item \phantomsection\label{comp:C3}\textbf{C3 --- Input Validation \& Sanitization Gate:} Service ingress validating UTF-8 text bounds (\MinTextLength{}--\MaxTextLength{}), static image formats (\texttt{PNG}/\texttt{JPEG}/\texttt{WebP}), byte size ($\le \MaxImageSize{}$), pixel dimensions (\MinImageDim{} to \MaxImageDim{}), and script stripping prior to inference (\texttt{FR2}, \hyperref[SR6]{SR6}; hazards \hyperref[haz:H2]{H2}, \hyperref[haz:H7]{H7}).
    \item \phantomsection\label{comp:C4}\textbf{C4 --- Request Isolation \& State Coordinator:} Assigns a cryptographically random, unguessable per-request token (\UUID{}v4 \texttt{req\_\allowbreak{}id}) bound to the initiating session, enforces \MaxResponseTime{} deadlines, handles cancellations, admits concurrent traffic up to \MaxConcurrentReqs{}, and gates optional external transfers (\texttt{FR6}, \texttt{FR8}, \texttt{FR10}, \texttt{FR11}, \hyperref[SR4]{SR4}, \hyperref[SR7]{SR7}, \hyperref[SR9]{SR9}; hazards \hyperref[haz:H6]{H6}, \hyperref[haz:H8]{H8}, \hyperref[haz:H9]{H9}).
    \item \phantomsection\label{comp:C5}\textbf{C5 --- Ephemeral Privacy \& Buffer Lifecycle Handler:} Blocks all persistent writes/logging of raw selections and stops request work while releasing application-owned transient payload references within \MaxRetentionTime{} of terminal completion, error, or cancellation (\texttt{FR9}, \texttt{NFR4}, \hyperref[SR8]{SR8}; hazard \hyperref[haz:H4]{H4}).
    \item \phantomsection\label{comp:C6}\textbf{C6 --- Signal Detection \& Grounded Evidence Engine:} Runs text/image detectors, \EXIF{}/\CTwoPA{} checks, domain/genre gates, and abstention logic, outputting source-tagged evidence (Observed Signal, External Reference, Model Inference) immune to injection (\texttt{FR3}, \texttt{FR4}, \texttt{FR7}, \texttt{FR13}, \hyperref[SR1]{SR1}--\hyperref[SR5]{SR5}; hazards \hyperref[haz:H1]{H1}--\hyperref[haz:H3]{H3}, \hyperref[haz:H6]{H6}).
    \item \phantomsection\label{comp:C7}\textbf{C7 --- Offline Benchmark \& Fairness Evaluation Workflow:} \CLI{} evaluation pipeline executing frozen candidate models on source-disjoint held-out datasets, logging eligibility/group/outcome records, full-population diagnostics, and \ESL{}/recompression slices (\texttt{FR12}, \texttt{FR14}, \texttt{NFR1}, \texttt{NFR7}, \texttt{NFR10}; hazard \hyperref[haz:H10]{H10}).
\end{enumerate}

\subsection{Entities Outside the System Boundary}
\begin{itemize}[leftmargin=*]
    \item \textbf{Primary User:} Selects webpage items, grants or denies optional external transfer consent, and interprets evidence/limitations.
    \item \textbf{Host Webpage \& Browser Runtime:} Untrusted third-party sites inside Chromium; all selected DOM data is treated as potentially hostile.
    \item \textbf{Optional External Provider:} Third-party API outside Team~23 control; disabled without documented zero-retention parity and per-request \HTTPS{} consent (\hyperref[SR4]{SR4}, \hyperref[SR8]{SR8}).
    \item \textbf{External Benchmark Corpora:} Read-only public evaluation datasets (e.g., HC3, RAID, GenImage) accessed solely by \hyperref[comp:C7]{C7}.
\end{itemize}

\section{Failure Mode and Effects Analysis}\label{sec:fmea}

This section defines the \FMEA{} method and qualitative severity scale, presents the component-level worksheet (Table~\ref{TblFMEA}), and assigns ownership and open verification gates (Table~\ref{TblRiskRegister}).

\subsection{FMEA Methodology, Control Hierarchy, and Qualitative Severity}
Following IEC 60812 \cite{IEC60812}, every internal component (\hyperref[comp:C1]{C1}--\hyperref[comp:C7]{C7}) is analyzed for failure modes, root causes, stakeholder harm, controls, and verification methods.

\noindent\textbf{Control Hierarchy:} We distinguish \textbf{[Elimination]} (removing an unsafe capability or code path completely when implemented and verified) from \textbf{[Mitigation]} (reducing exposure through validation, abstention, warnings, timeouts, and isolation). Planned requirements alone do not eliminate harm; non-accusatory phrasing removes direct insults without eliminating downstream misinterpretation, and random tokens do not replace authorization.

\noindent\textbf{Severity Only (No Speculative Likelihood Numbers):} Worst credible harm is rated qualitatively as \textbf{S1} (minor, reversible inconvenience), \textbf{S2} (material, recoverable disruption or local misattribution), or \textbf{S3} (serious reputational/academic accusation, financial deception, confidentiality leak, security exploit, or unsafe release decision). We intentionally omit quantitative or categorical likelihood ratings and conditional post-verification score reductions: open-world web content frequencies cannot be estimated without production telemetry, and passing pre-release tests verifies control behavior rather than real-world failure frequency. \textbf{At Revision~0, all controls are planned and every hazard remains Open (unverified).}

\section{Safety and Security Requirements}\label{sec:safety-reqs}

Derived from Table~\ref{TblFMEA}, the nine normative requirements \hyperref[SR1]{SR1}--\hyperref[SR9]{SR9} match Section~S.4 of the companion \SRS{} \cite{VeritySRS2026} identically. Hazard \hyperref[haz:H10]{H10} is governed directly by \SRS{} evaluation requirements \texttt{FR12}, \texttt{FR14}, \texttt{NFR1}, \texttt{NFR7}, and \texttt{NFR10}.

\subsection{User-Facing and Inference Safety Requirements (\texttt{SR1}--\texttt{SR5}, \texttt{SR7})}

\begin{enumerate}[leftmargin=*]
    \item \phantomsection\label{SR1}\textbf{SR1 --- Uncertainty Must Stay Visible}\newline
    Each completed assessment shall include explicit limitations and uncertainty information, and insufficient or conflicting evidence shall produce an \texttt{inconclusive} status rather than an unsupported authenticity or deception claim.

    \item \phantomsection\label{SR2}\textbf{SR2 --- No Accusation from a Detector Score}\newline
    The system result shall describe observed evidence and statistical signals about the submitted content item and shall not accuse its author, publisher, or depicted subject of fraud, dishonesty, or wrongdoing.

    \item \phantomsection\label{SR3}\textbf{SR3 --- No Safety or Authenticity Guarantee}\newline
    The system shall not describe any submitted item as guaranteed safe, authentic, or truthful, and shall instruct the user to verify the primary source independently before acting on high-stakes content.

    \item \phantomsection\label{SR4}\textbf{SR4 --- Safe Handling of Failed and Partial Analyses}\newline
    A request timeout ($\ge \MaxResponseTime{}$) or unrecoverable dependency failure shall produce a \texttt{failed} status, and partial signal output that cannot support an assessment shall produce an \texttt{inconclusive} status identifying the missing analysis; missing output shall never be mapped to evidence of low risk.

    \item \phantomsection\label{SR5}\textbf{SR5 --- Grounded Explanations and Prompt-Injection Immunity}\newline
    Every displayed factual assertion about a submitted item shall have a locator to an observed input signal or accessible external source that supports that assertion; model inferences shall be explicitly labelled and shall not be presented as verified facts. Instructions embedded within submitted text or image metadata shall never override this rule.

    \item \phantomsection\label{SR7}\textbf{SR7 --- Strict Request-to-Result Association}\newline
    Every displayed result shall be bound to exactly one initiating request identifier, and a late or out-of-order response from an earlier or cancelled submission shall never overwrite the result displayed for a newer submission.

\end{enumerate}

\subsection{Sandboxing, Privacy, and Isolation Requirements (\texttt{SR6}, \texttt{SR8}, \texttt{SR9})}

\begin{enumerate}[leftmargin=*, start=7]
    \item \phantomsection\label{SR6}\textbf{SR6 --- Untrusted Webpage Content Sandboxing}\newline
    The system shall reject unsupported or malformed inputs, shall never execute active content (HTML/JavaScript/SVG scripts) inside selected items, and shall enforce per-request payload size (\MinTextLength{}--\MaxTextLength{}, $\le \MaxImageSize{}$), dimension (\MinImageDim{} to \MaxImageDim{}), and execution time ($\le \MaxResponseTime{}$) bounds.

    \item \phantomsection\label{SR8}\textbf{SR8 --- Controlled Content Access and Ephemeral Cleanup}\newline
    The browser extension shall access webpage content only upon an explicit user-triggered check using least-privilege permissions, shall never collect unselected page content, browsing history, or credentials, shall require prior informed consent before any external provider transfer, shall never persist raw selected content, and shall stop request-owned processing and release application-owned transient copies within \MaxRetentionTime{} after every terminal outcome. External providers shall be disabled unless their documented retention terms are compatible with this policy; consent does not establish remote deletion.

    \item \phantomsection\label{SR9}\textbf{SR9 --- Cross-User and Cross-Session Isolation}\newline
    A user session shall not be able to retrieve, inspect, or receive another user's or concurrent session's submission or analysis result through predictable request identifiers or shared processing state.

\end{enumerate}

\subsection{Controls Deferred Beyond the Capstone Timeline}
Four post-capstone enhancements are explicitly deferred beyond April 2027:
\begin{enumerate}[leftmargin=*, noitemsep]
    \item \textbf{Firefox / Safari Store Extensions:} Capstone verification covers Chromium desktop \MVThree{} only.
    \item \textbf{Hardware Confidential Computing (\TEE{}):} Capstone backend uses \TLS{}/\HTTPS{} and application-level logical cleanup rather than hardware enclaves due to zero-budget constraints.
    \item \textbf{Audio / Video Deepfake Stream Controls:} Live media streams lie outside text and static-image scope (\SRS{} Section~G.6).
    \item \textbf{Production Distribution-Drift Telemetry:} Benchmarks lock static datasets per milestone rather than logging live user traffic telemetry.
\end{enumerate}

\section{Appendix --- Reflection}\label{sec:ha-reflection}

\input{../Reflection.text}

\begin{enumerate}
    \item What went well while writing this deliverable?
    \item What pain points did you experience during this deliverable, and how did you resolve them?
    \item Which of your listed risks had your team thought of before this deliverable, and which did you think of while doing this deliverable? For the latter ones (ones you thought of while doing the Hazard Analysis), how did they come about?
    \item Other than the risk of physical harm (some projects may not have any appreciable risks of this form), list at least 2 other types of risk in software products. Why are they important to consider?
\end{enumerate}

\subsection*{Calvin Salsali}
Writing the component-by-component FMEA forced our frontend decisions to answer directly to real harms instead of generic usability preferences. Before doing this analysis, I had already worried about false flags on honest writers (\hyperref[haz:H1]{H1}) and users treating a confidence number as proof (\hyperref[haz:H5]{H5}). What I had not thought of beforehand was \hyperref[haz:H8]{H8} (stale async overwrite) until Jaden and I traced a user highlighting two paragraphs back-to-back where the slow first response comes back last. Our biggest pain point in the November revision was cutting bloated repetition and removing the misleading ``low/moderate'' likelihood table rows (\href{https://github.com/richy1337/Verity/issues/63}{Issue \#63}) without losing concrete controls. Drawing on \textbf{SFWRENG 3RA3 (Software Requirements and Security Aspects)} and \textbf{SFWRENG 4HC3 (Human-Computer Interaction)}, two major non-physical software risks are \textbf{defamation/reputational harm} and \textbf{cognitive automation bias}, because interface phrasing can push a non-expert user to act unfairly on imperfect model output.

\subsection*{Raymond Tao}
Separating statistical \ML{} failures from deterministic elimination rules made it much clearer where Verity can promise behavior and where it has to stay conservative. Before writing the \HA{}, our team had already identified false positives (\hyperref[haz:H1]{H1}), missed synthetic content (\hyperref[haz:H2]{H2}), and benchmark leakage (\hyperref[haz:H10]{H10}). While examining the explanation generator inside \hyperref[comp:C6]{C6}, we uncovered \hyperref[haz:H3]{H3} (indirect prompt injection and fabricated citations) by asking what happens if selected webpage prose contains instructions meant for our explainer. A painful realization during the November revision---matching our Fall pilot results---was that our qualitative likelihood ratings gave a false sense of precision, so replacing them with open verification gates (\href{https://github.com/richy1337/Verity/issues/63}{Issue \#63}) and explicit false-positive notices (\href{https://github.com/richy1337/Verity/issues/65}{Issue \#65}) made the document far more honest. From \textbf{STATS 3Y03 (Probability and Statistics for Engineering)} and \textbf{SFWRENG 4AL3 (Applied Machine Learning)}, \textbf{demographic fairness bias} (such as higher \FPR{} on \ESL{} text) and \textbf{evaluation validity loss} are critical non-physical risks because hidden subgroup failures propagate directly into unfair decisions.

\subsection*{Jaden Moore}
Mapping components \hyperref[comp:C1]{C1}--\hyperref[comp:C7]{C7} cleanly across browser, team service, third-party API, and offline harness boundaries in Figure~\ref{fig:hazard-boundary} paid off immediately when aligning our architecture docs. Before this deliverable, I already expected dependency timeouts (\hyperref[haz:H6]{H6}), whereas tracing shared worker state and rapid request queues uncovered \hyperref[haz:H9]{H9} (cross-session state leakage) and the two-sided \hyperref[haz:H7]{H7} availability hazard—valid bursts saturating workers even when every single input is within size limits (\href{https://github.com/richy1337/Verity/issues/64}{Issue \#64}). Our main pain point was keeping \hyperref[SR1]{SR1}--\hyperref[SR9]{SR9} word-for-word identical with the \SRS{} while cutting the prose down by nearly half; relying on \texttt{verify\_specification.py --with-hazard} caught drift immediately. Informed by \textbf{SFWRENG 3BB4 (Concurrent System Design)} and \textbf{SFWRENG 3A04 (Software Design II)}, \textbf{cross-session data leakage} and \textbf{resource exhaustion under burst traffic} are essential software risks because concurrency bugs silently break isolation guarantees that sequential tests miss.

\subsection*{Richard Han}
Pinning each \FMEA{} failure mode directly to an automated or empirical \VnV{} test gave our test suite a concrete purpose. Before doing the \HA{}, I treated privacy mostly as ``don't log requests,'' whereas tracing cancellation and crash paths through \hyperref[comp:C5]{C5} surfaced the hidden retention leaks in \hyperref[haz:H4]{H4}, and examining untrusted DOM selections exposed SVG scripts and image decompression bombs in \hyperref[haz:H7]{H7}. The hardest pain point was trimming the landscape \FMEA{} table and standard descriptions down to scannable rows without dropping technical detail—checking the compiled PDF page-by-page showed how dense vertical grids buried the core Cause $\to$ Harm $\to$ Control story (\href{https://github.com/richy1337/Verity/issues/62}{Issue \#62}). Grounded in \textbf{SFWRENG 3S03 (Software Testing)} and \textbf{SFWRENG 3RA3 (Software Requirements and Security Aspects)}, \textbf{privacy compliance violations (\PIPEDA{})} and \textbf{untrusted input exploitation (\XSS{}/\DoS{})} matter deeply because a content-checking tool must never leak or endanger the user who asked for help.
